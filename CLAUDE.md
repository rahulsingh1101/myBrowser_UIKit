## Project overview

A macOS desktop web browser app. Despite the project name (`myBrowser_UIKit`), the UI framework is **AppKit/Cocoa** (`NSWindow`, `NSViewController`, `NSWindowController`), not UIKit — there is no iOS target. SwiftUI views are hosted inside AppKit view controllers for the home screen.

- Single target: `myBrowser_UIKit`, deployment target macOS 14.4 (`SDKROOT = macosx`).
- Persistence: Firebase Realtime Database (via Swift Package Manager), with local bundled JSON as an offline/first-run fallback; PDF library items additionally store a security-scoped bookmark (`Data`) rather than a raw file path, so file access survives relaunch under App Sandbox — see PDF library below. A Core Data model (`myBrowser_UIKit.xcdatamodeld`) exists but is currently unused.
- `GoogleService-Info.plist` is **not** checked into the repo (gitignored). Fetch it per-machine with `./scripts/fetch-firebase-config.sh` (requires Firebase CLI + Firebase project access — see script comments). This file was previously committed and leaked via GitHub secret scanning; history has been purged and the key rotated.

## Architecture

### Window management (the core abstraction)

The app is multi-window; window lifecycle is centralized rather than left to AppKit defaults. Understanding this requires reading across `RootWindow/` and `WindowControllers/`:

- **`AppWindowFactory`** (`RootWindow/AppWindowFactory.swift`) is the single entry point for creating any window, keyed by a `WindowType` enum (`.main`, `.browser(String)`, `.popup(WKWebViewConfiguration)`, `.browserPopup(configuration: WKWebViewConfiguration, urlString: String)`, `.reader(PDFLibraryItem)`). Each case's `WindowType.dedupeIdentifier` (`nil` for `.popup` only) declares whether/how it's de-duped; a second request for the same URL (via `.browser` or `.browserPopup`) or the same PDF item's `id` re-shows the existing window instead of opening a new one — bringing it forward as-is, without reloading it to the newly requested URL. `.popup` windows are never de-duped.
- **`WindowTracker`** (`RootWindow/WindowTracker.swift`) holds the registry of created/minimized/current windows and answers "what should Dock-click restore?" (`getWindowForDockClick`). It is constructed once, owned by `AppWindowFactory`, and injected into every window controller.
- **`RootWindowController`** (`RootWindow/RootWindowController.swift`) is the base class all window controllers inherit from; it implements `NSWindowDelegate` to report close/key/miniaturize events back into the shared `WindowTracker`.
- Concrete window controllers (`WindowControllers/MainContainerWindowController.swift`, `BrowserWindowController.swift`, `PopupWindowController.swift`, `ReaderWindowController.swift`) each own one `NSWindow` + root view controller pair and are created only through `AppWindowFactory.create(windowType:)` — never instantiate them directly.
- `AppDelegate` calls `windowFactory.create(windowType: .main)` on launch and again on Dock re-click (`applicationShouldHandleReopen`), routing through `WindowTracker.getWindowForDockClick()` so a minimized window is restored instead of duplicated.

### Browsing surfaces

- **`MainContainerController`** — the home window: a hamburger button + URL search field on top, `MenuContentController` (a SwiftUI-hosted grid/list of preloaded sites) below. Submitting a URL asks `AppWindowFactory` for a `.browser` window. The hamburger button shows an `NSPopover` (content: `HamburgerMenuView`, a SwiftUI list of `HamburgerMenuItem` cases) anchored below the button; picking an item calls `MenuContentController.select(_:)` and closes the popover.
- **`BrowserViewController`** — a standalone browser window: back/forward buttons + search field + `WKWebView`. `window.open()` / target=_blank navigation is handled via `WKUIDelegate.createWebView`, which asks `AppWindowFactory` for a `.browserPopup` window (a second `BrowserWindowController`/`BrowserViewController` pair, sized to 3/4 of the screen and centered), keyed by `navigationAction.request.url` so re-opening the same popup URL refocuses the existing window instead of stacking duplicates, and returns its `WKWebView` so WebKit renders into it — this gives popups the same address bar and back/forward chrome as a regular browser window. Back/forward buttons call `webView.goBack()/goForward()` and are enabled/disabled via KVO on `canGoBack`/`canGoForward`; the search field is kept in sync with the current URL via KVO on `webView.url` rather than `WKNavigationDelegate` callbacks, since those don't fire for same-document navigations (SPA `pushState`/`replaceState`). `BrowserViewController.init(configuration:)` takes an optional externally-built `WKWebViewConfiguration` — when supplied (the `.browserPopup` path) it's used as-is rather than the default self-built config, since WebKit requires the popup's webview to be constructed from the exact configuration it hands to `createWebView` (to preserve the opener relationship). `BrowserWindowController` exposes the resulting webview via a `webView` computed property for this purpose.
- **`PopupWindowController`** — bare `WKWebView` window, originally used for JS-opened popups before they were switched to `.browserPopup`; closes itself when the page calls `window.close()`. Currently unused (kept in place, not wired to any call site) in case a chrome-less popup is wanted again later.
- **`PDFReaderViewController`** / **`ReaderWindowController`** — a standalone PDF reader window, opened via `AppWindowFactory.create(windowType: .reader(item))`. `ReaderWindowController` just sizes the window and loads the given `PDFLibraryItem`; it has no reference to the PDF library's shared view model. Persistence is owned by the caller instead: `MenuContentController.openPDF` reaches the `PDFReaderViewController` via the reader window's `contentViewController` and, on `NSWindow.willCloseNotification`, `await`s `persistCurrentPage()` (async, saves `lastReadPage` via `FirebaseJSONRepository.updateElement`) before reloading its own `pdfLibraryViewModel` — sequenced in that order in one `Task` so the reload can't race the write.

### SwiftUI-in-AppKit bridging

`PreloadWindow/TaskListController/SwiftUIHostController.swift` is a generic `NSViewController` wrapper (`SwiftUIHostController<Content: View>`) for embedding any SwiftUI view inside the AppKit hierarchy. `MenuContentController` hosts three SwiftUI views this way: two `LibraryGridView` instances occupy the same frame and are toggled via `view.isHidden` depending on `currentMenuItem`, with `TaskListView` beside them:
- `LibraryGridView<Item>` / `LibraryCardView<Item>` (`PreloadWindow/Shared/Views/`) — one generic grid pane and card, used for both Home/Focus Music (`Item == ItemModel`) and PDF Library (`Item == PDFLibraryItem`). `Item` must be `Codable & Identifiable & LibraryDisplayable` (`Models/LibraryDisplayable.swift` — just `var title: String`; both models conform for free). Backed by `GenericLibraryViewModel<Item>` (`PreloadWindow/Shared/GenericLibraryViewModel.swift`), which takes the `FirebaseJSONRepository<[Item]>` as a parameter to `load(from:)`/`add(_:to:)`/`delete(_:from:)` rather than owning one — needed because the same `Item` type (`ItemModel`) is loaded/saved against a different repository per section (Home vs. Focus Music). `MenuContentController` holds `taskGridController: SwiftUIHostController<LibraryGridView<ItemModel>>` and `pdfLibraryController: SwiftUIHostController<LibraryGridView<PDFLibraryItem>>`, built in `makeGridView()`/`makePDFLibraryView()` with a per-type `subtitle` closure (a stored field for `ItemModel`; a derived "Last read: page N" string for `PDFLibraryItem` — kept as a closure rather than a `LibraryDisplayable` requirement since it's view formatting, not model data) and `onDelete` (conditional on `currentMenuItem == .home` for the grid; always present for the PDF library). On `select(_:)`, `.home`/`.focusMusic` re-render the grid via `taskGridController.updateRootView(_:)`; `loadContent(isInitial:)` then converts `currentMenuItem` to its `HamburgerMenuItem.itemModelSection` (`nil` for `.pdfLibrary`, which loads `pdfLibraryViewModel` directly instead — see Data layer below) and calls `menuContentViewModel.load(from: section.repository)`. Opening a Home/Focus Music card creates a `.browser` window; opening a PDF card creates a `.reader` window via `MenuContentController.openPDF`, which also registers a `willCloseNotification` observer that `await`s `PDFReaderViewController.persistCurrentPage()` then reloads `pdfLibraryViewModel` (see Browsing surfaces above). The `+` card (`AddTaskCardView`, same folder) is shared unchanged by both panes; for PDFs it presents an `NSOpenPanel` (`.pdf` only) or accepts a drop anywhere on the content view via `DropTargetView` (`MenuContentController`'s root view) — either path must create the security-scoped bookmark (`PDFBookmark.makeData`, `Services/PDFBookmark.swift`) synchronously in that callback, since deferring it past an actor hop can outlive the sandbox's access grant. `PDFBookmark` falls back to a plain, non-security-scoped bookmark if the security-scoped variant fails (local/unsigned-profile builds without App Sandbox properly provisioned).
- `TaskListView` (`PreloadWindow/TaskListController/Views/`) — the list pane, driven by a single `@MainActor` `ScrollViewViewModel` injected from `MenuContentController`, which owns its own fetch (`load()`, bound to `.scrollViewData()`). It is **not** menu-selection-switchable: `MenuContentController.loadContent(isInitial:)` only calls `scrollViewViewModel.load()` when `currentMenuItem == .home`, so selecting Focus Music or PDF Library leaves the list pane exactly as it was.

### Data layer

`Services/Firebase/`:
- `FirebaseBootstrap.configure()` — called once from `AppDelegate.applicationDidFinishLaunching`.
- `RealtimeDatabaseStore` (singleton) — thin async/await wrapper around `FirebaseDatabase` read/write at a given path; `RealtimeDatabaseError.noData` signals "nothing written at this path yet", not necessarily a failure.
- `FirebaseJSONRepository<Model: Codable>` — every Firebase-touching operation on an array-shaped model lives here in one file: `load()`/`save(_:)` (whole-array), plus `addElement(_:)`/`deleteElement(id:)`/`updateElement(id:mutate:)` for a single element, each load-mutate-save via a private `loadOrEmpty()` that treats `RealtimeDatabaseError.noData` as an empty array — so the first add against a path with no bundle fallback (e.g. `.pdfLibrary()`) doesn't fail — while still propagating any other error. `load()` itself falls back to a bundled JSON resource on failure *if one was provided* (`bundleFallbackResource` is optional — e.g. `.focusMusic()`/`.pdfLibrary()` have none and rethrow instead). New data types add a `static func` factory extension here (see `.preloadWebsites()`, `.scrollViewData()`, `.focusMusic()`, `.pdfLibrary()`) rather than constructing the generic type inline at call sites.
- `Models/HamburgerMenuItem.swift` — enum of hamburger-menu sections (`.home`, `.focusMusic`, `.pdfLibrary`). `itemModelSection: RepositoryBackedItemModel?` maps `.home`/`.focusMusic` to their `RepositoryBackedItemModel` case and `.pdfLibrary` to `nil`. `RepositoryBackedItemModel` (`Models/RepositoryBackedItemModel.swift`) is the two-case enum that owns `repository: FirebaseJSONRepository<[ItemModel]>` (`.preloadWebsites()`/`.focusMusic()`) — it simply has no `.pdfLibrary` case, so there's no way to ask it for a repository that doesn't exist. Adding another `[ItemModel]`-shaped section means adding a case to both enums plus a matching `FirebaseJSONRepository` factory. `.pdfLibrary` is driven entirely outside this pattern by `GenericLibraryViewModel<PDFLibraryItem>` / `FirebaseJSONRepository<[PDFLibraryItem]>.pdfLibrary()` (see SwiftUI-in-AppKit bridging above). If a new section needs its own list-pane data, give it a dedicated `ScrollViewViewModel` instance and repository in `MenuContentController`.
